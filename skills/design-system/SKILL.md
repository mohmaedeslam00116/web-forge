# Design System — encode the whole visual language

A design system is more than colors, fonts, radii, and buttons. It must carry the art direction into the real interface without flattening every page into one neutral component recipe.

## Source of truth

Inspect existing product identity, Design Passport, official design system files, current tokens/components, selected visualDirection, brand references, and actual assets. Preserve deliberate product conventions; replace them only when the user authorizes a redesign or evidence shows they are broken.

## Define only the roles the product needs

- color roles, semantic status, contrast pairs, and surface strategy;
- typography roles, language/glyph coverage, hierarchy, measure, and numeral rules;
- layout and spacing constraints;
- geometry, borders, surfaces, depth, lighting, and material treatment;
- image crops, aspect ratios, focal-point and overlay rules;
- illustration style, icon style, diagrams, data graphics, and map grammar;
- interaction states, motion language, reduced-motion behavior, and responsive transformations.

## Protect expressive range

Do not make every surface neutral just because a token system exists. Define surface-specific palettes, imagery, density, and composition where the product has different modes. A campaign can be expressive while the authenticated workspace remains restrained. A documentation surface can be typographic while a product gallery is image-led.

## Component contracts

For shared elements document: purpose, use when, do not use when, content limits, states, assets, responsive behavior, RTL behavior, accessibility, and performance. Reuse when semantics/behavior match, not just because the component looks similar.

## Validate in context

Test shared components in at least two real contexts. Check the page-level visual system as well as the component sheet. A cohesive design system may support varied pages; it must not force them to share one silhouette or visual weight.
